# On-screen keyboard options for Omarchy on a Surface tablet

Research checked 2026-09-23. Scope: text input after unlocking, a touchable icon in the top bar, a keyboard at the bottom or a smaller keyboard movable by touch. This is a review of upstream claims and code documentation, not a hardware test on the Surface.

## Existing projects

| Project | What already exists | Fit and gap |
| --- | --- | --- |
| [Gimbal](https://github.com/mechanicsunlocked/gimbal) | Omarchy 4 plugin with a top-bar keyboard icon and a GTK4 layer-shell keyboard; manual toggle, fixed top/middle/bottom positions, overlay or space reservation. It also integrates with fcitx5 for automatic appearance in supported text fields. | Closest integrated example. It explicitly targets the Framework Laptop 12 and says it was tested on one machine. Its touch-draggable objects are the two trigger knobs, not the keyboard. Its [known issues](https://github.com/mechanicsunlocked/gimbal/blob/master/KNOWN-ISSUES.md) say auto-show was measured in foot and GTK4, but has application gaps and has not yet been validated by a person touching the screen. |
| [tablet-kbd](https://github.com/ngek202/tablet-kbd) + [tablet-toggle](https://github.com/ngek202/tablet-toggle) | SAM OSK, a GTK4 layer-shell keyboard, manual invocation through a shortcut, edge gesture, or companion bar widget. It detects hardware and provides tablet rotation and gesture wiring. | Broader convertible target. Its companion icon toggles tablet mode; no movable keyboard is documented. Installing the whole stack would add much more than unlocked-session typing and includes the `lisgd` AUR dependency. |
| [omarchy-surface-touch](https://github.com/javon27/omarchy-surface-touch) | Built and tested on a Surface Pro 7+ under Omarchy 4. Its [OSK component](https://github.com/javon27/omarchy-surface-touch/tree/main/osk) runs `wvkbd-deskintl` with manual show/hide, and its [wvkbd patch](https://github.com/javon27/omarchy-surface-touch/tree/main/wvkbd) addresses touch jitter that made key highlights flicker and prevented repeat. | Strong Surface-specific starting point for the keyboard engine, but its keyboard is bottom docked. Its separate floating Quickshell component is a virtual trackpad, not a draggable keyboard, and the OSK component does not provide a bar icon. |
| [wvkbd](https://github.com/jjsullivan5196/wvkbd) | Established Wayland on-screen keyboard with mobile and desktop layouts, custom layouts, and show/hide/toggle signals. Its [manual](https://github.com/jjsullivan5196/wvkbd/blob/master/wvkbd.1.scd) offers full-width and left/right bottom docking, with an optional nonexclusive overlay. | Practical fixed bottom keyboard engine to test behind a bar button. Docking left or right is not free touch dragging. Its `--auto` option depends on compositor input-method support; test this separately, and keep manual toggle as the dependable entry point. |
| [Keystone OSK](https://github.com/svan71/keystone-osk) | Draggable, resizable full/compact keyboard with command-line show/hide/toggle. | Most direct floating-keyboard example, but its stated Wayland targets are GNOME and KDE, with no Hyprland result documented. It injects keys via `ydotool` and requires `ydotoold` and `/dev/uinput` access. Treat it as an experiment, not a confirmed Omarchy solution. |

There is direct Omarchy community demand: the [Framework 12 tablet discussion](https://github.com/omacom/omarchy/discussions/4431) specifically asks for an on-screen keyboard and links Gimbal. A separate [touchscreen discussion](https://github.com/omacom/omarchy/discussions/1659) reports limitations in touch-driven app launching. The search found the two Omarchy integrations above; this is not proof that no others exist.

## What Omarchy and Quickshell provide

Omarchy 4's own [shell plugin manual](https://github.com/omacom/omarchy/blob/quattro/manual/32-shell-plugins.md) says a plugin may contain a `bar-widget`, `panel`, and/or `service`. A user plugin lives in `~/.config/omarchy/plugins/`; `omarchy plugin validate` checks it. This is a clear route for a bar icon and settings UI. The user request concerns an **Omarchy shell plugin**, whose `manifest.json` differs from a **Codex plugin** and its `.codex-plugin/plugin.json` ([Omarchy manual](https://github.com/omacom/omarchy/blob/quattro/manual/32-shell-plugins.md)).

Quickshell's [PanelWindow documentation](https://quickshell.org/docs/types/Quickshell/PanelWindow) supports edge anchoring and an `exclusiveZone`, which provides the UI mechanics for a bottom docked surface that can reserve space. It does not by itself explain how QML key taps become keys in another application. Gimbal's [architecture note](https://github.com/mechanicsunlocked/gimbal/blob/master/ARCHITECTURE.md) describes a separate GTK4 keyboard sending real keycodes through Wayland's virtual-keyboard protocol while the Quickshell plugin manages the icon and state. That split is a proven implementation pattern within that project's test environment.

## Recommendation for a first version

1. Build only the unlocked-session bar toggle and a bottom docked keyboard first. Use Omarchy's `bar-widget` interface and test a maintained keyboard engine such as wvkbd on the actual Surface. Confirm touch typing into a GTK app, browser, and the user's terminal; confirm that tapping the icon again hides it and that application focus stays on the intended field. Gimbal documents a real [focus issue with layer-surface keyboards](https://github.com/mechanicsunlocked/gimbal/blob/master/KNOWN-ISSUES.md), so this is the main technical risk.
2. Treat the floating keyboard as a separate acceptance target. Gimbal provides only fixed positions and movable triggers, while Keystone offers the requested gesture but has no documented Hyprland support. Prototype a small movable layer surface or test Keystone on Hyprland before committing to an engine. Decide whether the floating board should overlay windows or reserve space; floating implies overlay.
3. Keep auto-show optional. The manual top-bar toggle works even in fields that do not publish Wayland text-input state; Gimbal's [known issues](https://github.com/mechanicsunlocked/gimbal/blob/master/KNOWN-ISSUES.md) call out client-specific gaps and incomplete hands-on validation. Leave lock-screen and hardware tablet-state integration for later as requested.

The most useful starting reference is Gimbal's [BarWidget.qml](https://github.com/mechanicsunlocked/gimbal/blob/master/BarWidget.qml), [Panel.qml](https://github.com/mechanicsunlocked/gimbal/blob/master/Panel.qml), and [architecture](https://github.com/mechanicsunlocked/gimbal/blob/master/ARCHITECTURE.md), while avoiding its Framework-specific fold and rotation code. Its auto-show behavior still needs testing on the Surface and in the applications the user actually types into.

## Surface Pro 4 compatibility and lock screen follow-up

Checked 2026-09-23 against the repositories' current `master` branches and read-only data from the Surface Pro 4 running this workspace. **Correction to the earlier scope note:** Gimbal and `omarchy-surface-touch` now each contain a lock-screen keyboard solution.

### Gimbal on this Surface Pro 4

Gimbal requires **Omarchy 4 on a Framework Laptop 12** by its [README](https://github.com/mechanicsunlocked/gimbal/blob/master/README.md#install). Its GTK4 keyboard, Omarchy bar widget, and Quickshell panel are potentially reusable on another Hyprland tablet, and its keyboard binary is manually available through `SUPER+B` even in laptop mode ([README](https://github.com/mechanicsunlocked/gimbal/blob/master/README.md#the-keyboard), [Panel.qml](https://github.com/mechanicsunlocked/gimbal/blob/master/Panel.qml)). That is a code-based portability assessment, not a Surface test.

The **unmodified package will not provide the requested touch workflow on the SP4**. Its [Lua hardware module](https://github.com/mechanicsunlocked/gimbal/blob/master/lua/gimbal.lua) detects tablet mode from a `gpio-keys` switch and a `cros-ec-lid-angle` sensor, then rotates from an `accel-display` sensor. It writes `gimbal-mode=tablet` only after those Framework-specific signals indicate folding. Its [bar widget](https://github.com/mechanicsunlocked/gimbal/blob/master/BarWidget.qml) shows the keyboard button only in that mode, the [panel](https://github.com/mechanicsunlocked/gimbal/blob/master/Panel.qml) normally starts its resident keyboard only in that mode, and its [lock clone](https://github.com/mechanicsunlocked/gimbal/blob/master/lock-clone/LockView.qml) shows the keypad only in that mode. On this SP4, read-only `/sys/bus/iio/devices/iio:device*/name` returns `gyro_3d`, `accel_3d`, `als`, `dev_rotation`; none is a `cros-ec-*` device. The running kernel is `6.19.8-arch1-3-surface`. A read-only input-device listing did not show a Framework `gpio-keys` tablet-mode source. Gimbal's [optional root boot fix](https://github.com/mechanicsunlocked/gimbal/tree/master/system) targets the Framework's `INT33D3`/Tiger Lake probe race and should not be applied to the SP4.

The [linux-surface feature matrix](https://github.com/linux-surface/linux-surface/wiki/Supported-Devices-and-Features#surface-tablets) lists the SP4 touchscreen, tablet mode, and sensors as supported, with the touchscreen marked as requiring the linux-surface kernel; this machine has that kernel. That establishes a plausible path for a **Surface-specific adapter**, not compatibility with Gimbal's sensor names. The adapter would need to detect a usable Type Cover/tablet state (including detached cover), provide a manual tablet-mode override so the bar icon and lock keypad remain reachable, and separately map the SP4 accelerometer's axes if rotation is wanted. The Type Cover detach case deserves explicit testing: a [linux-surface report for another Surface Pro generation](https://github.com/linux-surface/linux-surface/issues/846) found a tablet switch when folded but not when detached. The keyboard's Framework key legends and six-row geometry may also be less comfortable on the SP4, though they are not a protocol blocker ([keyboard source](https://github.com/mechanicsunlocked/gimbal/blob/master/osk/oskbd.c)).

### Existing lock-screen approaches

| Project | Lock-screen status | Fit and caveat |
| --- | --- | --- |
| [Gimbal](https://github.com/mechanicsunlocked/gimbal/blob/master/README.md#the-lock-screen) | Has a QML password keypad inside a clone of `omarchy.lock`. Its [installer](https://github.com/mechanicsunlocked/gimbal/blob/master/install.sh) offers to clone the lock plugin and patch Omarchy's current `LockView.qml`; it leaves PAM alone. | The keypad is hidden until Gimbal reports `tablet`, which this SP4 cannot currently do. The [lock instructions](https://github.com/mechanicsunlocked/gimbal/blob/master/lock-clone/README.md) require a physical keyboard available for the first real lock test. Gimbal's [testing checklist](https://github.com/mechanicsunlocked/gimbal/blob/master/TESTING.md#the-lock-screen-checkpoint-4) still has unchecked real-lock, wrong-password, fingerprint, and idle-lock cases. Clones require attention after Omarchy updates; the installer warns if its patch no longer applies ([known issues](https://github.com/mechanicsunlocked/gimbal/blob/master/KNOWN-ISSUES.md)). |
| [omarchy-surface-touch](https://github.com/javon27/omarchy-surface-touch/tree/main/lock-pin) | Has a numeric PIN pad plus QWERTY keyboard inside a lock-screen plugin, developed on an SP7+. It supports account-password entry too. | Its [installer](https://github.com/javon27/omarchy-surface-touch/blob/main/lock-pin/install.sh) also installs a new `/etc/pam.d/omarchy-lock-password` and adds a separate PIN using `libpam_pwdfile`. That changes authentication and needs root. Its [hardware note](https://github.com/javon27/omarchy-surface-touch/blob/main/README.md#hardware-compatibility) says the lock component should be portable to other Surface models, but SP4 lock-screen operation is undocumented. The QML keypad is a useful reference even if a new PIN is unwanted. |
| [tablet-kbd](https://github.com/ngek202/tablet-kbd) | No lock-screen keypad or lock-plugin clone found in its README, installer, or `kbd/` code. | Its session keyboard cannot solve a secure session lock by itself. |

The key architectural limit is the secure session lock: ordinary keyboard layer surfaces are hidden and cannot receive touch while locked. The keypad must be drawn inside the lock surface, as [Gimbal explains](https://github.com/mechanicsunlocked/gimbal/blob/master/lock-clone/README.md#why-it-cannot-ship-in-the-plugin) and as the [Omarchy Surface Pro lock request](https://github.com/omacom/omarchy/discussions/9600) describes. Neither solution addresses the earlier boot-time disk-unlock prompt; Gimbal documents that separately in [LUKS.md](https://github.com/mechanicsunlocked/gimbal/blob/master/LUKS.md).

**Recommendation:** reuse Gimbal's keyboard, bar UI, and lock-keypad design only after separating them from the Framework fold signal. For the SP4, make the bar button available without automatic tablet detection first, validate touch typing and focus, then adapt the lock clone with a Surface/manual mode signal and test an actual lock while a physical keyboard remains available. Avoid installing Gimbal's Framework boot fix. If a separate PIN is desired later, evaluate `omarchy-surface-touch`'s PAM change as a distinct security decision.
